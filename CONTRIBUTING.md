# Contributing

Thank you for contributing to MountainGuard-AI.

## Principle

> **Scientific corrections are more valuable than additional features.**

## Who can contribute

Students and professionals from AI/ML, IoT, GIS, geology, glaciology, hydrology, telecommunications, emergency management, UX, accessibility, software engineering, data engineering, research, and education are welcome.

## Pull-request expectations

- explain the problem being solved
- keep educational/demo assumptions explicit
- add tests for behavioral changes
- never present synthetic thresholds as scientific thresholds
- cite scientific claims added to documentation
- do not add real emergency-service integrations
- preserve `EXERCISE — EDUCATIONAL SIMULATION` markings
- update `SAFETY.md` when changing safety-relevant behavior

## Good first issues

- improve sensor-quality scoring
- add missing-data simulations
- create dashboard charts
- add multilingual **test** alert examples
- add accessibility improvements
- improve documentation
- add model evaluation reports
- add synthetic scenario replay

## Code style

- Python type hints
- small functions
- clear naming
- no embedded credentials
- configuration outside business logic
- docstrings for public functions
- tests for risk logic

## Scientific contributions

For domain models, include references and clearly state:

- where the model is valid
- where it is not valid
- what data it expects
- uncertainty
- validation method

Do not merge claims of real predictive ability without evidence.
